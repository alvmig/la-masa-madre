La Masa Madre

gtag.js nativo, sin Tag Manager. Una SPA de verdad, instrumentada de cero.

Presentación. Preguntar quién ha tocado GA4 / UA / GTM antes. Dejar claro que todo lo que veamos está en un repo público y que la web del teléfono es real: los eventos que dispare durante la clase aparecen en DebugView.

Qué vamos a hacer

  • Instrumentar una tienda desde cero con gtag.js.
  • Medir un embudo de ecommerce completo, de view_item_list a purchase.
  • Depurar lo que enviamos: DebugView, Network, tests automáticos.
  • Consentimiento: qué se manda cuando el usuario dice que no.
  • Leer los datos: informes, Exploraciones, BigQuery.
  • Meter datos sin navegador: Measurement Protocol.

Todo el código: github.com/alvmig/la-masa-madre

Este teléfono acompaña toda la formación. Es la web real servida desde el mismo dominio que las slides: por eso el iframe no es de terceros y las cookies funcionan igual que en una pestaña normal.

Alta y configuración

Lo que hay que tener montado antes de escribir una línea de código.

Este bloque es el "de dónde sale todo esto". Lo hacemos en vivo sobre la propiedad de la formación para que vean cada pantalla.

Crear la propiedad

  • Administrar → Crear → Propiedad.
  • Zona horaria y moneda: se fijan aquí y condicionan todos los informes. Europe/Madrid y EUR.
  • Luego, flujo de datos web: la URL es informativa, no filtra nada.
Una propiedad GA4 puede tener varios flujos (web, iOS, Android) y los datos se mezclan. Un flujo ≠ una vista de Universal Analytics: las vistas ya no existen.

El Measurement ID

Flujo de datos → arriba a la derecha: G-TCCFCHKDG9.

Es público: va en el HTML de todo el mundo. No es un secreto y no autentica nada: cualquiera puede mandar eventos a tu propiedad si lo conoce.

Lo que sí es un secreto es el API secret del Measurement Protocol (mismo panel, más abajo). Ese nunca va al frontend.

Bloque 1.1

El modelo de eventos

En GA4 todo es un evento

No hay pageviews, ni eventos con categoría/acción/etiqueta, ni transacciones aparte. Solo:


gtag('event', '<nombre>', { <parámetros> });
  • Una vista de página es un evento: page_view.
  • Una compra es un evento: purchase.
  • Tu evento propio es un evento: solicita_presupuesto.

Viniendo de Universal Analytics: olvida categoría / acción / etiqueta. No existen.

Cuatro familias de eventos

FamiliaQuién los mandaEjemplo
Automáticosla libreríasession_start, first_visit
Medición mejoradala librería, configurablescroll, click, file_download
Recomendadostú, con nombres fijospurchase, add_to_cart
Personalizadostú, nombre librepide_hogaza_gigante
Los recomendados son los que desbloquean informes ya hechos. purchase alimenta los informes de ingresos; compra_finalizada no alimenta nada.

Parámetros: la parte que se olvida

  • Cada evento lleva parámetros. Muchos se registran solos (page_location, language…).
  • Para ver un parámetro propio en los informes hay que registrarlo como dimensión personalizada.
  • Hay cupo: 50 dimensiones de evento por propiedad. No es infinito.
Regla práctica: si vas a segmentar por ello, es dimensión personalizada. Si solo lo quieres para depurar, con verlo en DebugView basta.

Bloque 1.2

gtag.js por dentro

Nuestro arranque, comentado

Lo importante: gtag es un push a un array. Todo lo que llamas antes de que cargue la librería se encola y se procesa en orden. Por eso el orden del consentimiento importa aunque el script aún no esté.

Por qué funciona antes de cargar nada


window.dataLayer = window.dataLayer || [];
function gtag() { dataLayer.push(arguments); }

gtag() no envía nada: encola. Cuando gtag/js carga, procesa la cola en orden.

Consecuencia práctica: el orden de tus llamadas se respeta aunque la red vaya lenta o el script esté bloqueado.

Qué viaja por el cable

Un evento = una petición a /g/collect con todo en la query string.


en=add_to_cart            nombre del evento
cu=EUR                    currency
epn.value=11              parámetro numérico
ep.item_list_id=catalogo  parámetro string
pr1=idMM-HOG-01~nmHogaza…~pr5.5~qt2~lp0   item 1
gcs=G111                  estado de consentimiento
epn. = número, ep. = string. Si mandas value como "11" viaja como ep.value y GA4 no lo suma. Este es el fallo número uno de ingresos.

Bloque 1.6

Consent Mode v2

El orden es lo único que importa

  1. dataLayer + stub de gtag
  2. gtag('consent', 'default', {…}) ← antes de todo lo demás
  3. carga de gtag/js
  4. gtag('config', …)
La documentación es literal: "the order of the code here is vital". Con config antes del default, los defaults no se aplican.

Las cuatro señales

SeñalQué controla
analytics_storagecookie _ga (la que nos importa)
ad_storagecookies publicitarias
ad_user_dataenvío de datos a Ads
ad_personalizationpersonalización de anuncios

Denegado no es silencio

Con analytics_storage: 'denied', gtag sigue enviando pings sin cookie ni identificador.

  • gcs=G100 → denegado
  • gcs=G111 → concedido

GA4 los usa para modelar lo que no puede medir.

Lo que salió antes de aceptar no se reenvía: esos eventos quedan sin identificar para siempre.

Demo en vivo: rechazar en el teléfono, enseñar en Network gcs=G100 y la ausencia de cookie _ga en Application. Luego aceptar y ver G111.

Bloque 2.1

Informes vs Exploraciones

Dos productos distintos dentro de la misma herramienta.

Antes: el ámbito de los datos

Todo dato en GA4 tiene un ámbito. Mezclarlos es la causa nº 1 de informes que no cuadran.

ÁmbitoEjemplo de dimensiónEjemplo de métrica
Eventoevent_name, page_locationrecuento de eventos
Itemitem_name, item_categoryingresos por artículo
Sesiónfuente/medio de la sesiónsesiones, tasa de interacción
Usuarioprimera fuente, paísusuarios totales
"Ingresos por campaña" ¿usa la campaña de la sesión o la de primera visita? Son números distintos y los dos son correctos. Cuando alguien diga "esto no cuadra", empieza preguntando por el ámbito.

Los cuatro informes del ciclo de vida

  • Adquisición — de dónde vienen. Usuarios nuevos vs sesiones.
  • Interacción — qué hacen. Eventos, páginas, tiempo.
  • Monetización — qué compran. Aquí aterriza tu purchase.
  • Retención — si vuelven.

Más "Tiempo real" y "DebugView", que ya usamos ayer.

Los informes estándar se apoyan en tablas agregadas: por eso van rápidos y por eso no puedes preguntarles cualquier cosa.

Dónde te mienten (1): muestreo

GA4 puede responder con una muestra y escalar el resultado.

PropiedadLímite por consulta
Estándar10 millones de eventos
360hasta 1.000 millones

Se ve en el icono de calidad de datos arriba del informe, con el porcentaje usado.

Mira ese icono siempre antes de copiar una cifra a un informe. Un 8 % de muestra en un embudo de nicho es ruido con aspecto de dato.
En la cuenta demo hay volumen suficiente para provocarlo: filtrar por país y rango largo suele disparar el muestreo. Enseñarlo en vivo.

Dónde te mienten (2): la fila (other)

Cuando una tabla tiene demasiadas filas, GA4 deja las más frecuentes y mete el resto en (other).

  • La documentación no publica un número fijo: depende de la consulta.
  • Regla que sí da: más de 500 valores distintos = dimensión de alta cardinalidad.
  • Afecta más a Exploraciones que a informes estándar.
Por eso nunca metas un ID de usuario, un transaction_id o un timestamp en una dimensión personalizada. Te comes el cupo y ensucias todas las tablas.

Dónde te mienten (3): umbrales

GA4 oculta datos cuando podrían identificar a alguien: demografía, intereses, consultas de búsqueda.

Mensaje típico: "Se ha aplicado un umbral a una o varias tarjetas de este informe".

  • Se dispara sobre todo con señales de Google activadas y pocos usuarios.
  • BigQuery no aplica umbrales… pero tampoco recibe datos de señales de Google.
Consecuencia práctica: los totales de la interfaz y los de BigQuery no van a coincidir exactamente. Y las dos cifras son "correctas".

Bloque 2.3

BigQuery

Donde se acaban las excusas de la interfaz.

Por qué exportar

  • Sin muestreo y sin umbrales. Los datos crudos, evento a evento.
  • Sin límite de cardinalidad. Todos los transaction_id que quieras.
  • Joins con lo tuyo: márgenes, devoluciones, CRM, coste real de cada pedido.
  • Histórico tuyo. Si mañana borras la propiedad, los datos siguen ahí.
La exportación no es retroactiva: empieza a llenarse el día que la activas. Actívala hoy aunque no la vayas a usar hasta dentro de un año.

Las dos exportaciones

DiariaStreaming
Frecuencia1 vez al díaminutos
Tablaevents_YYYYMMDDevents_intraday_YYYYMMDD
Límite (estándar)1 millón de eventos/día—
Coste extrano~0,05 $/GB (≈600.000 eventos)
Pegallega por la tardesin fuente/medio en usuarios nuevos

La tabla intradía se borra cuando se completa la diaria de ese día.

Cinco cosas del esquema que hay que interiorizar

  1. Una fila = un evento. No una sesión, no un pedido.
  2. Los parámetros no son columnas: viven en event_params, con cuatro cajones de tipo.
  3. Los items tampoco: items es otro array dentro de la fila.
  4. No hay session_id: hay ga_session_id, y solo es único junto a user_pseudo_id.
  5. Tablas diarias: events_* + _TABLE_SUFFIX, que es lo que controla el coste.

1 · El comodín de fecha

_TABLE_SUFFIX no es un WHERE cualquiera: decide qué tablas se leen, y por tanto lo que pagas.

2 · UNNEST, el patrón que repetirás toda tu vida

Si el parámetro es numérico, string_value viene NULL. De ahí el COALESCE que verás en todas partes.

Truco: documentar una propiedad que no conoces


SELECT p.key, COUNT(*) AS veces
FROM `…events_*`, UNNEST(event_params) AS p
WHERE _TABLE_SUFFIX = '20210131'
GROUP BY p.key ORDER BY veces DESC

La forma más rápida de saber qué mide de verdad una web que acabas de heredar.

Lo mismo con event_name te da el inventario de eventos.

3 · Qué es una sesión aquí

La clave es siempre user_pseudo_id + ga_session_id.

4 · El embudo, explícito

Lo que en Exploraciones es un clic, aquí se puede versionar, revisar en un PR y programar.

5 · Ingresos por producto: la trampa clásica

Si haces UNNEST(items) y sumas purchase_revenue, cuentas el pedido una vez por producto. Es el error más común de este dataset.

6 · Auditar tu propia medición

Coste: cómo no llevarte un susto

  • Se paga por bytes escaneados, no por filas devueltas. LIMIT no abarata nada.
  • SELECT * escanea todas las columnas. Pide solo las que uses.
  • Filtra siempre por _TABLE_SUFFIX.
  • El editor te dice el coste estimado antes de ejecutar. Míralo.
  • El sandbox da 1 TB al mes gratis, sin tarjeta.

Comprobación honesta: bq query --dry_run te da los bytes sin ejecutar nada.

Las seis juntas: menos del 0,1 % del terabyte gratuito mensual.

Lo que se puede hacer y en la interfaz no

  • LTV real por canal de captación, con el margen de tu ERP.
  • Atribución propia: la de GA4 es una caja negra; aquí decides tú.
  • Detección de fallos de medición: eventos sin parámetros obligatorios, value nulo, duplicados.
  • Alimentar modelos: recomendación, propensión a comprar, churn.
El ejercicio de la última consulta de /sql es precisamente ese: comparar tres formas de calcular los ingresos y explicar por qué no coinciden.

Bloque 2.4

Measurement Protocol y server-side

Cuándo lo necesitas de verdad

  • Una devolución que se aprueba tres días después, en tu back-office.
  • Un pago diferido (transferencia, contrarreembolso) que confirma el banco.
  • Una baja de suscripción procesada por un cron.
  • Una compra por teléfono que mete un comercial.
  • Rellenar una propiedad de demo… como hicimos para esta formación.
Lo que no es: un sustituto de gtag.js. Sin navegador no hay dispositivo, ni geografía, ni referrer, ni medición mejorada.

La petición


POST https://www.google-analytics.com/mp/collect
     ?measurement_id=G-TCCFCHKDG9&api_secret=SECRETO
    

{
  "client_id": "1699642630.1789889256",
  "timestamp_micros": "1789889256061000",
  "events": [{
    "name": "purchase",
    "params": {
      "transaction_id": "MM-1789889256-VO1P",
      "currency": "EUR", "value": 15.6, "tax": 1.56, "shipping": 3.5,
      "items": [{ "item_id": "MM-HOG-01", "price": 5.2, "quantity": 3 }],
      "session_id": "1789827990",
      "engagement_time_msec": 434
    }

Mismos nombres que en el navegador: el tracking plan no cambia porque cambie el transporte.

Las cuatro reglas que se saltan todos

  1. session_id y engagement_time_msec o no cuenta como sesión ni como interacción.
  2. 72 horas de retroactividad. Más atrás, GA4 acepta el evento y le cambia la fecha en silencio.
  3. Límites: 25 eventos por petición, 25 parámetros por evento, cuerpo < 130 kB.
  4. client_id: si no es el mismo del navegador, es otro usuario. Y ahí se rompe la atribución.

El problema del client_id

El usuario compra en el navegador y tu backend confirma el pago dos días después. ¿Cómo sabe GA4 que es la misma persona?


// En el navegador, al confirmar el pedido: guárdalo con el pedido.
gtag('get', MEASUREMENT_ID, 'client_id', (cid) => {
  fetch('/api/pedido', { method: 'POST',
    body: JSON.stringify({ transaction_id, ga_client_id: cid }) });
});

Tu backend lo almacena junto al pedido y lo reutiliza cuando manda el refund.

Sin esto, la devolución se atribuye a un usuario fantasma y los ingresos netos por canal quedan mal para siempre.

Seguridad

  • El Measurement ID es público: cualquiera puede mandar eventos falsos a tu propiedad. Se asume.
  • El API secret no: variable de entorno en el servidor, nunca en el frontend ni en el repo.
  • Si se filtra, se revoca y se crea otro desde el flujo de datos.

En este repo: site/config.js lleva el ID; el secreto vive en simulator/.env, gitignored.

Checklist para revisar cualquier implementación

  1. ¿Hay un tracking plan escrito? Si no, no hay nada que revisar.
  2. ¿Los eventos usan los nombres recomendados?
  3. ¿value es numérico y lleva currency?
  4. ¿Los items llevan item_id en todos los eventos?
  5. ¿purchase puede dispararse dos veces? Recarga y "atrás".
  6. ¿Cuántos page_view por navegación? Cuéntalos.
  7. ¿El consentimiento va antes del config?
  8. ¿Hay un test que lo verifique en CI?
